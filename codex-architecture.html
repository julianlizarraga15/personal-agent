02 · Bot resources

Only three things are mounted

Conversation threads are not among them. They live only in memory and disappear when the bot restarts.

Read + write

/workspace

The project files Codex may inspect, edit, and test. /project can narrow the working directory beneath this root.

Private volume

/codex-home

ChatGPT authentication and Codex configuration. Login survives container replacement; sandboxed project commands cannot read it.

Private volume

/trace-state

The protected trace store also holds the atomic 100-request UTC daily API-Football counter. Sandboxed commands cannot read it.

03 · Security boundary

Workspace power, not host power

A named workspace profile blocks sensitive mounts and public network access. It allows one credential-safe analytics socket; exact public HTTPS still needs owner approval.

Codex can

Work like a coding agent inside the selected project.

  • Read and modify workspace files
  • Run local commands and project tests
  • Use uv to create and manage Python projects
  • Query approved analytics through api-football
  • Request one exact HTTPS destination with owner buttons
  • Continue a thread across Telegram messages
  • Report progress and return formatted answers

Codex does not get

The credentials or mounts needed to control the host.

  • No Docker socket or deployment queue
  • No SSH key or Git push credential
  • No OpenAI or API-Football API key
  • No writes outside the workspace sandbox
  • No other private/local or unapproved shell networking
  • No reads of Codex auth, trace state, or .env
04 · Separate control plane

Deployment is manual and isolated

This lane is not connected to Telegram or Codex. It exists only for a trusted host operator.

Builds and replaces the bot only when the trusted checks pass.

Key separation: the bot can edit the repository, but it cannot ask the deployer to run those edits. Only a published, matching commit can cross this boundary through a trusted manual workflow.
